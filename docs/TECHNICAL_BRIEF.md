# SOA-MX10 v3.0  
## Technical Brief — Deterministic Execution-Control Protocol

---

## 1. Scope and Purpose

This document specifies **SOA-MX10 v3.0**, a deterministic execution-control protocol for computing systems that incorporate AI components.

The protocol governs **whether computational operations are permitted to execute**.  
It does **not** govern AI behavior, reasoning, alignment, or content generation.

AI outputs are treated as **untrusted proposals**. Execution authority is enforced externally through cryptographically verifiable authorization artifacts and a non-AI execution controller.

This document is a **specification**, not an implementation.

---

## 2. Problem Statement

AI-orchestrated systems frequently rely on prompts, policies, or post-hoc logging to influence behavior. Such approaches:

- do not prevent execution of unauthorized operations
- rely on AI compliance
- permit fallback or tool bypass
- fail under adversarial or malformed outputs

SOA-MX10 addresses these limitations by introducing **mandatory execution gating** that makes unauthorized execution **technically impossible**, independent of AI output.

---

## 3. Design Goals

The protocol is designed to satisfy the following non-negotiable goals:

1. **Execution Impossibility Without Authorization**  
   No operation may execute without cryptographic authorization.

2. **AI as Untrusted Input**  
   AI components may propose actions but never authorize or execute them.

3. **Deterministic Enforcement**  
   Authorization decisions are deterministic and non-AI.

4. **Fail-Closed Semantics**  
   Any ambiguity, invalidity, or absence of authorization halts execution.

5. **Minimal Trusted Computing Base**  
   The verification component is intentionally small and auditable.

6. **Formal Specifiability**  
   The protocol is reducible to a finite state machine.

---

## 4. System Overview

At a high level, SOA-MX10 separates **proposal**, **verification**, and **execution** into distinct roles:

- **Proposal**: Generated by AI or other untrusted sources
- **Verification**: Performed by a deterministic kernel
- **Execution**: Gated by an execution controller

No component may combine all three roles.

---

## 5. Core Components

### 5.1 Execution Gate (EG)

The **Execution Gate** is a non-AI control module that intercepts all operation invocations, including:

- tool calls
- external system interactions
- fallback execution paths

**Function**  
The Execution Gate prevents invocation of any operation unless a valid **Execution Receipt** is presented.

**Properties**
- Non-bypassable
- Fail-closed
- Independent of AI outputs

---

### 5.2 Verification Kernel (VK)

The **Verification Kernel** is a deterministic, non-AI verifier responsible for validating authorization artifacts.

**Permitted Functions**
- cryptographic signature verification
- monotonic counter validation
- state-transition validation
- receipt generation
- append-only logging

**Explicit Exclusions**
- no inference
- no policy interpretation
- no reasoning
- no AI execution

The Verification Kernel is intentionally minimal to reduce attack surface and ambiguity.

---

### 5.3 State Transition Token (STT)

A **State Transition Token (STT)** is a cryptographically constructed authorization artifact required to request execution of an operation.

**Conceptual Fields**
- previous state hash
- next state identifier
- operation identifier
- operation payload hash
- monotonic counter
- session nonce
- policy hash
- timestamp
- signature

**Properties**
- state-bound
- non-replayable
- single-use
- cryptographically verifiable

An STT may be proposed by an untrusted component but must be verified by the Verification Kernel.

---

### 5.4 Execution Receipt (ER)

An **Execution Receipt** is generated solely by the Verification Kernel upon successful verification of an STT.

**Purpose**
- proves authorization of a specific operation
- binds execution to a verified state transition

**Requirement**
The Execution Gate permits execution **only** when a valid Execution Receipt is presented.

---

### 5.5 Append-Only Ledger (AL)

The **Append-Only Ledger** records verified execution events.

**Properties**
- tamper-evident
- write-only
- ordered by monotonic counter

The ledger supports auditability and fork detection.

---

## 6. Execution Flow (Conceptual)

1. An untrusted component proposes an operation and submits an STT.
2. The Verification Kernel validates the STT.
3. If valid, the Verification Kernel emits an Execution Receipt.
4. The Execution Gate permits execution only upon receipt validation.
5. Execution is recorded in the Append-Only Ledger.

At no point does an AI component authorize or execute an operation directly.

---

## 7. Formal Execution Semantics

### 7.1 Fail-Closed Invariant

> Absence, invalidity, or ambiguity of an authorization artifact SHALL result in prevention of operation execution.

There is no best-effort execution mode.

---

### 7.2 Fallback as a Secured Execution Path

Fallback execution is treated as a **distinct execution path**, not a retry or model switch.

Each fallback path:
- requires a separate STT
- is bound to the same policy and state lineage
- is subject to the same Execution Gate

Fallback cannot bypass authorization requirements.

---

## 8. State Machine Compatibility

The protocol is reducible to a finite state machine with:

- explicitly defined states
- allowed transitions
- terminal halt states

Any invalid transition results in a halt condition.

(See `PROTOCOL_FSM.md`.)

---

## 9. Threat Assumptions

**In Scope**
- adversarial or deceptive AI outputs
- malformed authorization artifacts
- replay attempts
- unauthorized execution requests

**Out of Scope**
- operator compromise
- hardware compromise
- cryptographic primitive failure

(See `THREAT_MODEL.md`.)

---

## 10. Non-Goals and Explicit Exclusions

SOA-MX10 does not claim to provide:

- AI alignment
- content moderation
- ethics enforcement
- model behavior guarantees

The protocol controls **execution eligibility only**.

---

## 11. Technical Improvement Summary

SOA-MX10 improves computer operation by:

- preventing unauthorized execution paths
- enforcing deterministic execution order
- eliminating reliance on AI compliance
- binding execution to cryptographically verified state transitions

These improvements are independent of AI model internals.
