# SOA-MX10 v3.0  
## Authorization Artifacts Specification

---

## 1. Purpose

This document defines the **authorization artifacts** used by the SOA-MX10 v3.0 execution-control protocol.

Authorization artifacts are data objects that:
- represent execution eligibility
- bind execution to verified state transitions
- are evaluated by non-AI enforcement components

This document specifies **conceptual structure and required properties** only.  
It does not define serialization formats, cryptographic parameters, or implementation details.

---

## 2. Artifact Categories

SOA-MX10 defines two primary authorization artifacts:

1. **State Transition Token (STT)**
2. **Execution Receipt (ER)**

These artifacts are mandatory for execution authorization.

---

## 3. State Transition Token (STT)

### 3.1 Role

A State Transition Token (STT) is an authorization request artifact that represents a proposed transition from one execution state to another.

An STT:
- may be constructed by untrusted components
- has no execution authority by itself
- must be verified by the Verification Kernel

---

### 3.2 Required Conceptual Fields

An STT SHALL conceptually include the following fields:

- **previous_state_hash**  
  Identifies the immediately preceding committed execution state.

- **next_state_identifier**  
  Identifies the proposed next execution state.

- **operation_identifier**  
  Identifies the operation proposed for execution.

- **operation_payload_hash**  
  Cryptographic digest representing the operation payload.

- **monotonic_counter**  
  Strictly increasing counter bound to the session.

- **session_nonce**  
  Session-unique identifier preventing cross-session reuse.

- **policy_hash**  
  Digest binding the STT to a specific policy configuration.

- **timestamp**  
  Logical or physical time indicator (non-authoritative).

- **signature**  
  Cryptographic signature binding the above fields.

The specific encoding of these fields is implementation-defined.

---

### 3.3 Required Properties

An STT MUST satisfy the following properties:

- **State-Bound**  
  Valid only for the referenced prior state.

- **Single-Use**  
  Cannot be reused for multiple executions.

- **Non-Replayable**  
  Reuse SHALL be detected and rejected.

- **Non-Fungible**  
  Cannot be substituted for another operation or state transition.

- **Verifiable**  
  Subject to deterministic verification by the Verification Kernel.

---

## 4. Execution Receipt (ER)

### 4.1 Role

An Execution Receipt (ER) is an authorization confirmation artifact generated exclusively by the Verification Kernel.

An ER:
- represents verified execution eligibility
- authorizes exactly one execution event
- is required by the Execution Gate to permit execution

---

### 4.2 Required Conceptual Fields

An ER SHALL conceptually include the following fields:

- **receipt_identifier**  
  Unique identifier for the receipt.

- **authorized_operation_identifier**  
  Identifier of the authorized operation.

- **state_transition_hash**  
  Digest of the verified state transition.

- **confirmed_monotonic_counter**  
  Counter value confirmed during verification.

- **verification_result**  
  Outcome of authorization verification (e.g., authorized).

- **kernel_signature**  
  Cryptographic signature of the Verification Kernel.

---

### 4.3 Required Properties

An ER MUST satisfy the following properties:

- **Kernel-Originated**  
  Generated only by the Verification Kernel.

- **Execution-Bound**  
  Valid for a single execution attempt only.

- **Non-Replayable**  
  Reuse SHALL result in execution prevention.

- **Non-Forgeable**  
  Cryptographically verifiable as kernel-issued.

---

## 5. Artifact Lifecycle

### 5.1 STT Lifecycle

1. STT is constructed by an untrusted component.
2. STT is submitted to the Verification Kernel.
3. STT is either rejected or verified.
4. Verified STTs are consumed and cannot be reused.

---

### 5.2 ER Lifecycle

1. ER is generated by the Verification Kernel.
2. ER is presented to the Execution Gate.
3. ER authorizes exactly one execution attempt.
4. ER is consumed and invalidated after use.

---

## 6. Artifact Enforcement Rules

The following enforcement rules SHALL apply:

- Execution SHALL NOT occur without a valid ER.
- STTs SHALL NOT authorize execution directly.
- Any artifact reuse SHALL result in a halt condition.
- Artifact mismatch SHALL result in execution prevention.

These rules are enforced structurally, not by convention.

---

## 7. Failure Conditions

Artifact-related failures that SHALL result in execution prevention include:

- missing artifact
- malformed artifact
- signature verification failure
- counter reuse or regression
- policy hash mismatch
- state lineage mismatch
- artifact reuse

---

## 8. Relationship to FSM

Authorization artifacts are evaluated in accordance with the formal FSM defined in `PROTOCOL_FSM.md`.

Artifacts do not alter FSM structure.  
Artifacts only enable or block state transitions.

---

## 9. Non-Goals

This document does not define:
- artifact encoding formats
- cryptographic algorithms
- key management procedures
- transport mechanisms

These details are intentionally excluded.
